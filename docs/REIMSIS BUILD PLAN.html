REIMSIS

Reimbursement Management System. Med Refs encode receipts with evidence, a Checker verifies them, an Approver decides. Every step is audited, emailed, and ends in a printable reimbursement document and liquidation report.

StackReact + Vite, Node/Express (TypeScript), MySQL, Prisma
Scale50–500 users, queue for email and reports
Roles nowMed Ref, Checker, Approver, Super Admin
Roles laterAccounting, added as data, not code

System architecture

One API owns every rule. The browser never talks to the database or the file store.

Frontend

  • React 18, Vite, TypeScript
  • Tailwind, responsive tables become cards on phones
  • TanStack Query for data, React Hook Form + Zod
  • PDF.js style viewer for evidence preview

Backend

  • Express + TypeScript, feature folders
  • Prisma ORM and migrations
  • Multer for upload, Pino for logs
  • PDFKit (documents), ExcelJS (XLSX), fast-csv

Repo

  • Monorepo: apps/api, apps/web, packages/shared
  • Shared package holds status enums, permission codes, Zod schemas
  • Local dev on XAMPP MySQL, Redis optional (falls back to DB queue)

Access control page and profile page

Two new pages. Access control is for the Super Admin. Profile is for everyone.

Access control page Super Admin

  • Users tab: list, search, filter by role and status. Create user, edit details, assign role, activate or deactivate, reset password, force logout, unlock a locked account.
  • Roles tab: list of roles with rank and user count. Create a role, rename it, set its rank.
  • Permission matrix: a grid of roles against permissions, grouped by area (Receipts, Evidence, Review, Reports, Users, Audit). Tick or untick, review the pending changes, then save.
  • Sessions tab: active logins per user with device and last seen, and a revoke button.
  • Every change is written to the audit log with before and after values.

Guard rails

  • Built-in roles cannot be deleted. Their core review permissions are locked so nobody can remove the only approver path by accident.
  • The last active Super Admin cannot be deactivated or demoted.
  • A role in use cannot be deleted. Its users must be moved first.
  • Permission changes apply to existing sessions within a minute, not only at next login.
  • Rank decides who can manage whom: you can only edit users ranked below you.

Profile page Everyone

  • Details: name, email, phone, position or branch, profile photo (JPG or PNG, resized on upload). Email and role are read-only for the user; only the Super Admin changes them.
  • Security: change password with strength meter, see active sessions and sign out other devices, last login time.
  • Notification preferences: mute the optional emails and digests. Required emails (return, approve, disapprove, reserve) cannot be turned off.
  • My access: read-only list of what the signed-in role can do, so users know why a button is missing.
  • My activity: my recent actions, pulled from the audit log.
  • Appearance: light, dark or follow the device.

Decision

Permissions are set per role only. There are no per-user overrides in v1. It keeps the matrix easy to read and audit. If someone needs different access, give them a different role.

End-to-end workflow

Who does what, and what the system does in response.

Status rules

One module enforces these transitions. Controllers cannot set a status directly.

TransitionWhoRequired inputSide effects
Draft → SubmittedMed Ref (owner)At least one evidence file, valid amount and dateNotify Checkers
Submitted → CheckedCheckerRemarks; evidence viewed at least onceNotify Approvers
Submitted → ReturnedCheckerRemarks (what to fix)Email Med Ref
Returned → SubmittedMed RefEdited recordNotify Checkers, keep earlier remarks
Checked → ApprovedApproverOptional remarkEmail, build reimbursement document
Checked → DisapprovedApproverReason (mandatory)Email with reason
Checked → ReservedApproverNote (mandatory)Email with note
Reserved → CheckedApproverOptional remarkIn-app notice to Med Ref

Each transition carries the record's version. If another reviewer acted first, the request fails with a clear message instead of overwriting.

Evidence handling

View, download and print all go through one endpoint. The audit row is written first, so no view goes unrecorded.

Upload rules

  • JPG, PNG, WEBP, HEIC, PDF
  • 10 MB per file, 10 files per receipt (configurable)
  • Check the real file signature, not only the extension
  • SHA-256 stored, duplicates flagged
  • Random file names on disk, original name kept in the DB

Preview

  • Images: zoom and rotate inside the app
  • PDF: page viewer inside the app
  • Print opens the file in a print-ready view
  • Phones: camera capture straight into the upload field

After submission

  • Evidence is locked while Submitted, Checked or Reserved
  • It can change only in Draft or Returned
  • Removing a file is a soft delete and stays in the audit trail

Emails go through the queue with retries and a row in email_log, so a down SMTP server never blocks an approval. Each user can mute the optional ones.

Monitoring view

  • Med Ref: my records by status, anything returned or reserved at the top.
  • Checker: submitted queue, oldest first, with age badges.
  • Approver: checked queue, reserved list, totals pending by amount.
  • Super Admin: all of the above plus a live activity feed and the audit browser (filter by user, action, entity, date range; export to CSV).

Documents, reports, import and export

Reimbursement document

  • One per approved receipt, created by the worker right after approval
  • Numbered REIM-2026-000001
  • Lists receipt details, approver, dates, evidence count
  • Download and print from the record page
  • Layout is a placeholder until your boss's manual form arrives

Liquidation report

  • Approved records only, enforced in the query, not the UI
  • Filter by date range, Med Ref, category, document number
  • PDF, XLSX or CSV, with totals
  • Stored and listed, so it can be downloaded again
  • Template is also a placeholder for now

Import / export

  • Import CSV or XLSX as Drafts, with a downloadable template
  • Preview shows valid rows and row-level errors before anything is saved
  • Every list exports what its filters show
  • Imports are audited as one job plus one row per record

Security and scalability

Security

  • Argon2 password hashes, httpOnly secure cookies, CSRF token
  • Permission check on every route, plus record-level ownership checks
  • Rate limit on login and upload, account lockout after repeated failures
  • Evidence only through authorised endpoints
  • Audit table is insert-only at the database level
  • Secrets in environment variables, never in the repo

Scalability

  • Storage adapter: swap disk for S3 without touching features
  • Queue keeps email and reports off the request path
  • Indexes on status, encoder, dates and audit entity
  • Roles and permissions as data, ready for Accounting
  • API is stateless, so it can run as several instances

Quality

  • Unit tests on the state machine and permission rules
  • API tests for every transition, including the forbidden ones
  • Playwright for the main journey on phone and desktop sizes
  • Seed script with one user per role and sample receipts

Delivery phases

Estimates assume one full-time developer. They are for ordering the work, not a promise.

Weeks 1–2

1 · Foundation

Monorepo, MySQL schema and migrations, auth, roles and permissions, audit middleware, base layout with responsive shell, profile page and access control page (users, roles, permission matrix, sessions).

Done when: all four roles can log in and see an empty dashboard, every login is in the audit log, the Super Admin can change a role's permissions and a user sees the change within a minute, and each user can edit their profile and password.
Weeks 2–3

2 · Med Ref flow

Receipt form, drafts, evidence upload, in-app viewer, download and print, submit.

Done when: a Med Ref can encode, attach a photo and a PDF, preview both, and submit.
Weeks 3–5

3 · Checker and Approver

State machine, queues, review workspace, remarks, return, approve, disapprove, reserve, release, evidence-view audit.

Done when: the full flow runs end to end and every forbidden transition is rejected by tests.
Week 6

4 · Notifications

Queue and worker, email templates, in-app bell, email log with retries.

Done when: approve, disapprove, reserve and return each send the right email.
Weeks 7–8

5 · Documents and reports

Reimbursement document, liquidation report in PDF, XLSX and CSV, print views. Placeholder templates.

Done when: approving creates the document, and a report contains approved records only.
Weeks 8–9

6 · Import, monitoring, audit browser

CSV and XLSX import with preview, list exports, monitoring dashboards, admin audit log, user management.

Done when: an import with bad rows reports each error and saves only valid rows after confirmation.
Week 10

7 · Polish and release

Phone and desktop QA, accessibility pass, real templates from your boss, backups, deployment guide.

Done when: a non-developer completes the full flow on a phone without help.
